* Emacsの構築

** 構成

init.el と conf/ 以下の *.el は役割で分割している。新しい設定を足すときは、この分類に沿って該当ファイルに追記する。

*** init.el

最小限のブートストラップだけを担当する。
- ロケール・文字コードの設定
- straight.el 自体のブートストラップ(パッケージマネージャ本体の導入)
- custom.el の読み込み
- load-path の追加
- conf/ 以下の各ファイルを、依存順に ~load~ する

*** conf/*.el

機能ごとに分割していて、init.el から次の順(依存順)で読み込まれる。

| ファイル          | 役割                                                                                                                                                                            |
|-------------------+---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| basic.el          | フォント・見た目・Dired基本設定・バックアップ設定・PATH同期など、Emacs本体の基礎設定。パッケージへの依存が薄い設定が中心。                                                      |
| package-manage.el | straight.el/use-packageによる各種パッケージの導入・設定(evil、補完(corfu/orderless/prescient)、Magit、vterm、gptel等)。プログラミング言語以外の汎用パッケージはここに集約する。 |
| ai-agent.el       | AIエージェントCLI(claude/agy/bob)のvterm起動設定と、gptel・whisperの設定。                                                                                                      |
| ai-client.el      | AIの応答をJSONストリーム(claude CLI / Gemini API / 独自OpenAI互換API)として受け、ツール呼び出しや思考をEmacsのバッファへ描くクライアント。                                      |
| language.el       | プログラミング言語・マークアップ/データ形式のメジャーモード、および言語サーバ(eglot)・Lintの設定。                                                                              |
| mylisp.el         | 既存パッケージに依存しない自作のユーティリティ関数(OS標準アプリで開く、Boxnote作成 等)。                                                                                        |
| mail.el           | メール(mu4e)の設定。mu4eのelispは mu 本体に同梱されるため straight 管理外で、mu が入っていない環境では設定ごと無効になる(下記「メール(mu4e)」参照)。                            |
| keybind-manage.el | 全てのキーバインド定義。パッケージ設定側にキーバインドを書かず、ここに集約して一覧性を保つ。                                                                                    |

load順が重要になる場合がある(例: keybind-manage.el は package-manage.el で定義された関数・キーマップを参照するため最後に読み込む)。

** パッケージ管理の思想

- パッケージマネージャは package.el/ELPA ではなく [[https://github.com/radian-software/straight.el][straight.el]] を使用している。
  - gitのコミット単位でバージョンを固定でき、~straight/versions/default.el~ の lockfile をコミットすることで別マシンでも同一状態を再現できる(ELPA/MELPAはバージョンの巻き戻し・固定がしづらい)
  - MELPAに存在しないパッケージもGitHubから直接取得できる(例: ~:straight (corfu :type git :host github :repo "minad/corfu" ...)~)
- パッケージの導入・設定は [[https://github.com/jwiegley/use-package][use-package]] で統一している。~:straight t~ を必ず付け、~:defer~/~:hook~/~:commands~ などで遅延読み込みし起動時間を抑える。
- 1つのuse-packageブロックにキーバインドをベタ書きせず、キーバインドは keybind-manage.el 側にまとめる。設定(何を有効化するか)とキー割り当て(どのキーで呼ぶか)を分離することで、キーバインドの一覧性・変更のしやすさを保っている。
- lockfileの更新(新しいパッケージ追加後や、意図的な最新化)は下記「別マシンへの移行」を参照。

*** macOSのEmacsビルド (emacs-mac)

macOSでは Homebrew の [[https://github.com/railwaycat/homebrew-emacsmacport][railwaycat/emacsmacport]] tap から emacs-mac をビルドして使う。

- 標準のNSビルド(Homebrewの ~emacs~ formula や ~emacs-app~ cask)は *stipple非対応* で、indent-bars がロード時に "Invalid face box" エラーになり動かない。emacs-mac(Mitsuharu Macポート)は stipple に対応しているため indent-bars がそのまま綺麗に描画できる。
- Emacs 30実験版(~emacs-mac@30exp~)も存在するが、native-comp の eln 参照周りが不安定だったため、安定版の ~emacs-mac@29~ (Emacs 29.4) を採用。eglot・tree-sitter・native-comp・json はいずれも29.4で利用可能。

#+begin_src sh
# ビルド(初回はソースからのビルドで時間がかかる)
brew install railwaycat/emacsmacport/emacs-mac \
  --with-native-comp --with-mac-metal --with-unlimited-select \
  --with-librsvg --with-xwidgets --with-starter

# CLIの emacs/emacsclient を張り替え
brew link --overwrite emacs-mac

# /Applications に Emacs.app のエイリアスを作成
osascript -e 'tell application "Finder" to make alias file to posix file "/opt/homebrew/opt/emacs-mac/Emacs.app" at POSIX file "/Applications"'
#+end_src

別ビルドから乗り換えた直後は、straightのビルド済み成果物と native-comp キャッシュを一度消して作り直すと安全:

#+begin_src sh
rm -rf ~/.emacs.d/straight/build ~/.emacs.d/eln-cache
#+end_src


*** その他の準備

- 環境変数HOMEに `~` の定義
- 環境変数ANTHROPIC_API_KEY(gptelのAnthropicバックエンドで使用)
- Node.js は [[https://github.com/Schniz/fnm][fnm]] で管理する(LTSのv24系を使用)。

  #+begin_src sh
  brew install fnm
  fnm install 24 && fnm default 24
  #+end_src

  ~.zshrc~ には下記を書く(順序に意味がある。詳細は次の段落)。

  #+begin_src sh
  # FNM_DIR の既定は "~/Library/Application Support/fnm" でPATHにスペースが入るため寄せる
  export FNM_DIR="$HOME/.local/share/fnm"
  export PATH="$PATH:$FNM_DIR/aliases/default/bin"
  eval "$(fnm env --use-on-cd --shell zsh)"
  #+end_src

  GUI起動のEmacsは basic.el の exec-path-from-shell が ~zsh -l -i~ を起動してPATHを取り込むので、
  ~.zshrc~ に書けば同期される。ただし ~fnm env~ がPATHの先頭に足すのは *シェルごとの一時ディレクトリ*
  (~~/.local/state/fnm_multishells/<pid>_<時刻>~ 。実体は ~aliases/default~ へのsymlink)で、
  そのシェルが終われば消える。Emacsは起動時に取り込んだPATHを持ち続けるため、それだけだといずれ
  nodeを見失う。そこで default バージョンへの *安定したパス* を先に末尾へ足しておき、
  そのあとに ~fnm env~ で一時ディレクトリを先頭に載せる(通常のシェルでは ~.node-version~ に応じた
  切り替えが効き、Emacsから見ると最低限 default のnodeが常に見つかる、という二段構えにする)。

  続けて言語サーバとフォーマッタをまとめて入れる(Go/Rustは別経路なので下表を参照):

  #+begin_src sh
  npm install -g prettier vscode-langservers-extracted typescript typescript-language-server \
    pyright bash-language-server yaml-language-server
  #+end_src

  npmのグローバルパッケージは *Nodeのバージョンごと* に入る。~fnm default~ で別バージョンへ
  切り替えたときは、上記のインストールをやり直す。

- Markdownプレビュー(grip-mode)用に *go-grip* を PATH の通った場所へ置く。straightの管理外なので、lockfileから復元しても入らない点に注意。Goツールチェーンは不要で、配布バイナリを展開するだけでよい

  #+begin_src sh
  VER=v0.9.2
  curl -fsSL -o /tmp/go-grip.tar.gz \
    "https://github.com/chrishrb/go-grip/releases/download/$VER/go-grip-$VER-darwin-arm64.tar.gz"
  tar xzf /tmp/go-grip.tar.gz -C /tmp
  install -m 755 /tmp/go-grip /opt/homebrew/bin/go-grip
  # Apple Siliconでは未署名バイナリが起動を拒否されるためad-hoc署名を付ける
  codesign -s - -f /opt/homebrew/bin/go-grip
  #+end_src

  素の ~grip~ (Python版)でも grip-mode は動くが、レンダリングをGitHub APIに投げるため書きかけの本文が外部送信され、レート制限(60回/時)もかかる。go-gripは完全ローカルで動き、mermaid・数式・シンタックスハイライトのJS/CSSを同梱するのでオフラインでも崩れない。~grip-command~ で go-grip を明示指定している(language.el)。
- (macOS・任意) GNU coreutils の `gls` を入れておくとDiredの表示が改善する(`--group-directories-first`等)。未導入でも標準のlsで動作する
- (macOS・任意) `trash` コマンドを入れておくと削除がゴミ箱に移動する(未導入時はEmacs標準の削除挙動になる)
- (macOS注意) emacs-mac(Mac port)は press-and-hold(押し続けるとアクセント記号選択ポップアップが出る機能)を *デフォルトで無効化* する実装になっている([[https://github.com/railwaycat/homebrew-emacsmacport][NEWS-mac]] 参照、~ApplePressAndHoldEnabled~ を明示的に ~YES~ にしない限りoff)。そのため vanilla Cocoa Emacs や emacs-plus 向けの定番Tips(~defaults write org.gnu.Emacs ApplePressAndHoldEnabled -bool false~)は emacs-mac では基本不要(設定しても無害だが効果はない)。
- (macOS注意) evilのhjkl等キーを押しっぱなしにした時の移動が遅いと感じる場合、真因は上記ではなく *macOSのキーリピート速度(グローバル設定)* が新規マシンでは控えめな初期値のままであることが多い。System Settings > キーボード の「キーリピート」「リピート入力認識までの時間」を最速側に寄せるか、下記で調整する(Emacsに限らずOS全体のキー入力に影響するため、変更前に必ず確認すること)。

  #+begin_src sh
  defaults write -g KeyRepeat -int 2          # 数値が小さいほど速い(既定値未設定時は中庸)
  defaults write -g InitialKeyRepeat -int 15  # リピート開始までの遅延。小さいほど早く開始
  #+end_src

  反映にはログアウト/再ログイン、またはアプリの再起動が必要な場合がある。

** 初回起動(パッケージの事前ダウンロード)

新しいマシンでの初回起動は、straight.el が lockfile 記載の全パッケージ(約90個)を clone/build するため時間がかかる。特に GUI(Emacs.app)から起動するとダウンロード中は画面が無反応になり「固まった」ように見える。下記の手順で *シェルから事前取得* しておくと、進捗がターミナルに出て、GUI をロックせずに済む。

*** 手順

1. (推奨) recipe リポジトリ nongnu-elpa を軽量取得しておく
   straight は既定で nongnu-elpa を [[https://git.savannah.gnu.org][git.savannah.gnu.org]] から *全ブランチ* clone する。savannah は帯域が細く、これが初回フリーズの主因。単一ブランチ・浅い clone にしておけば数秒で済み、straight は origin URL が一致するためこれをそのまま使う(重い再取得をしない)。

   #+begin_src sh
   mkdir -p ~/.emacs.d/straight/repos
   git clone --single-branch --depth 1 \
     https://git.savannah.gnu.org/git/emacs/nongnu.git \
     ~/.emacs.d/straight/repos/nongnu-elpa
   #+end_src


2. init.el が参照する空ディレクトリを用意する(無いと load-path 構築で停止する)

   #+begin_src sh
   mkdir -p ~/.emacs.d/public_repos
   #+end_src


3. バッチ(非GUI)でパッケージを一括 clone / build する

   #+begin_src sh
   emacs --batch -l ~/.emacs.d/init.el
   #+end_src

   straight.el のブートストラップ → 各パッケージの clone/build が進み、進捗がターミナルに出る。~EXIT 0~ で終われば ~straight/repos/~ に約90個のリポジトリが揃う。事前に PATH へ go/npm 等を通した状態で実行すると、言語サーバ連携まわりの警告も減る。


4. 通常どおり GUI で起動する。パッケージは取得済みなので固まらない。

*** Emacs 30 対応(設定側で対処済み)

Emacs 30 では pin している一部パッケージがそのままでは動かないため、設定側で対処している(新規に lockfile を作り直す際も同様の対処が要る)。

- ~init.el~: straight.el が参照する ~native-comp-deferred-compilation-deny-list~(Emacs 30 で削除)を、未定義なら補う互換シムを bootstrap 前に定義している。これが無いと straight のネイティブコンパイル時に ~void-variable~ で停止する。
- ~conf/package-manage.el~: git-gutter+ が依存宣言する git-commit の recipe が現行 recipe リポジトリから消滅した(magit に統合された)ため、magit リポ内の ~lisp/git-commit.el~ を指す recipe を明示して解決させている。


*** transient / magit の "static-when" エラー(原因と修正)

起動時に次のような警告が出ることがある(use-package が捕捉するため起動自体は継続する)。

#+begin_example
Invalid function: static-when
transient--init-suffix-key is already defined as something else than a generic function
#+end_example

**原因**: transient / magit は compat 由来のマクロ ~static-when~ を使う。ところが straight が
~build-cache.el~ にこれらの依存を =nil= と記録してしまうことがあり(特にビルドが途中で中断された
場合)、その状態でビルドすると compat が load-path に入らないまま byte-compile され、~static-when~
が *展開されず関数呼び出しとして .elc に残る*。起動時に「Invalid function: static-when」で transient
のロードが不完全になり、Emacs 30 組込 transient(0.7.x)と ~transient--init-suffix-key~ の定義が
衝突して magit / magit-section / git-gutter+ まで巻き込む。

**修正**: 依存(compat/cond-let/llama 等)を読み込んだ状態で該当パッケージを byte-compile し直す。
~static-when~ を使うのは ~transient.el~ と ~magit-base.el~ だが、道連れになる magit 一式もまとめて
再コンパイルすると確実。

#+begin_src sh
emacs --batch --eval '(let ((b (expand-file-name "~/.emacs.d/straight/build/")))
  (dolist (p (directory-files b t))
    (when (file-directory-p p) (add-to-list (quote load-path) p)))
  (dolist (r (quote (compat cond-let llama dash with-editor))) (ignore-errors (require r)))
  (dolist (pkg (quote ("transient" "magit" "magit-section" "git-commit" "with-editor" "git-gutter-plus")))
    (dolist (el (directory-files (expand-file-name pkg b) t "\\.el$"))
      (ignore-errors (byte-compile-file el)))))'
#+end_src

再コンパイル後に Emacs を再起動すれば解消する。~.el~ ソースは変更しないので straight は再ビルドせず、
この修正した ~.elc~ がそのまま使われる(~straight/build~ を消して作り直すと再発しうる)。

*** 言語サーバー(eglot)を使う場合

Emacs30標準の eglot で、プログラミング言語ごとに言語サーバーを自動起動する設定を language.el に入れている。Emacs自体には同梱されていないため、使いたい言語の分だけ別途インストールする(未インストールでもEmacsの起動やそれ以外の言語の編集には影響しない)。

| 言語           | 実行ファイル               | インストール例                                                                         |
|----------------+----------------------------+----------------------------------------------------------------------------------------|
| Python         | pyright                    | ~npm install -g pyright~                                                               |
| TypeScript     | typescript-language-server | ~npm install -g typescript typescript-language-server~                                 |
| Go             | gopls                      | ~go install golang.org/x/tools/gopls@latest~                                           |
| Rust           | rust-analyzer              | ~brew install rustup~ → ~rustup default stable~ → ~rustup component add rust-analyzer~ |
| Shell          | bash-language-server       | ~npm install -g bash-language-server~                                                  |
| CSS/SCSS       | vscode-css-language-server | ~npm install -g vscode-langservers-extracted~                                          |
| Terraform      | terraform-ls               | ~brew install hashicorp/tap/terraform-ls~                                              |
| Bicep          | Bicep.LangServer.dll       | ~brew install dotnet~ のあとEmacsで ~M-x bicep-install-langserver~                     |
| CloudFormation | yaml-language-server       | ~npm install -g yaml-language-server~                                                  |

Go と Rust は導入先がPATHに載らないので、~.zshrc~ に下記を足しておく(前者は ~go install~ の
出力先、後者は keg-only な rustup のshim置き場。どちらもEmacsからは exec-path-from-shell 経由で見える)。

#+begin_src sh
export PATH="$PATH:$(go env GOPATH)/bin"
export PATH="$PATH:/opt/homebrew/opt/rustup/bin"
#+end_src

同様に、uv で入れたCLI(cfn-lint等)は ~~/.local/bin~ に入る。~uv tool update-shell~ を一度実行すると
~.zshenv~ にPATHが追記される。

(macOS注意) Emacs.appなどGUIから起動したEmacsは、ターミナルの ~.zshrc~ 等で設定したPATHを引き継がない。npmのグローバルインストール先や ~~/.go/bin~ 等に上記を入れてもeglotが見つけられないことがあるため、basic.el で [[https://github.com/purcell/exec-path-from-shell][exec-path-from-shell]] を使いシェルのPATHをEmacsに同期している(通常は追加設定不要)。

*** 保存時の自動フォーマット(apheleia)

保存すると apheleia が外部フォーマッタを非同期で実行する(VSCodeの "Format on Save" 相当)。
どのモードでどのフォーマッタを使うかは apheleia の既定表(~apheleia-mode-alist~)に従うので、
設定側では有効化だけしている。フォーマッタ本体は別途インストールする。

| 対象                    | 実行ファイル | インストール例            |
|-------------------------+--------------+---------------------------|
| TypeScript/TSX/CSS/JSON | prettier     | ~npm install -g prettier~ |
| Python                  | black        | ~pip install black~       |

プロジェクトの ~node_modules/.bin~ にフォーマッタがあれば、グローバルより優先して使われる。

*** Lint (flycheck)

言語サーバとは別に、flycheck から外部のLinterを呼ぶ設定が language.el にある。

| 対象           | 実行ファイル | インストール例             |
|----------------+--------------+----------------------------|
| CloudFormation | cfn-lint     | ~uv tool install cfn-lint~ |

CloudFormationは、テンプレートの中身(~AWSTemplateFormatVersion~)を ~magic-mode-alist~ で
見て cfn-json-mode / cfn-yaml-mode に振り分けている(拡張子が ~.json~ / ~.yaml~ のままで
ファイル名からは判別できないため)。YAML側は eglot + yaml-language-server にも繋いでいて、
スキーマ(SchemaStoreが案内するCloudFormationのJSON Schema)から補完とホバーが効く。
cfn-lint はスキーマ検証では拾えないCFN固有の規則を見るので、両方を併用している。
Goだけは従来どおり ~gofmt-before-save~ (goimports)に任せ、二重に整形が走らないよう apheleia の対象から外している。

*** tree-sitter grammar (TypeScript/TSX/CSS)

~.tsx~ / ~.jsx~ はJSXを含むため、~typescript-mode~ では字下げもハイライトも崩れる。
Emacs29内蔵のtree-sitterモード(~tsx-ts-mode~ / ~typescript-ts-mode~)を使うが、grammarは各マシンでのビルドが必要。
下記を一度実行してEmacsを再起動する(Cコンパイラとgitが要る)。

: M-x my/treesit-install-grammars

未導入の間は従来の ~typescript-mode~ で開くようにしてあるので、実行しなくても編集自体はできる
(その場合はJSXの字下げが崩れる)。

** Emacsビルドの切り替え (emacs-plus 30 ⇔ emacs-mac 29)

macOSでは2つのEmacsを共存させ、用途で使い分けている。設定はビルドごとに *git ブランチ* を分けている。

| ビルド        | Homebrew                                    | CLI(~emacs~)              | GUI                              | 設定ブランチ  | indent 表示             |
|---------------+---------------------------------------------+---------------------------+----------------------------------+---------------+-------------------------|
| emacs-plus 30 | ~emacs-plus@30~ (tap d12frosted/emacs-plus) | ~brew link emacs-plus@30~ | ~/Applications/Emacs-plus30.app~ | ~main~        | highlight-indent-guides |
| emacs-mac 29  | ~emacs-mac@29~                              | ~brew link emacs-mac@29~  | ~/Applications/Emacs-mac29.app~  | ~emacs-mac29~ | indent-bars(stipple)    |

両者とも native-comp 有効の Cocoa ビルドで、Cellar に併存できる。CLI の ~emacs~ はどちらか一方だけが
~/opt/homebrew/bin/emacs~ を張れる(リンクの排他)。旧構成(emacsformacosx = cask ~emacs-app~ +
ターミナル版フォーミュラ ~emacs~)は emacs-plus@30 に置き換えた。emacs-plus は新しい tap のため
初回は ~brew tap d12frosted/emacs-plus && brew trust d12frosted/emacs-plus~ が要る。

*** 切り替え手順(両方向で対称)

30→29 と 29→30 は *ミラーの同一手順* で、入れ替える formula 名と checkout するブランチが逆になるだけ。

1. CLI のリンクを張り替える(現行を unlink → 対象を link)

   #+begin_src sh
   # 30 → 29
   brew unlink emacs-plus@30 && brew link emacs-mac@29
   # 29 → 30
   brew unlink emacs-mac@29  && brew link --overwrite emacs-plus@30
   #+end_src

2. 設定ブランチを切り替える

   #+begin_src sh
   git checkout emacs-mac29   # 29用 (30へ戻すときは main)
   #+end_src

3. GUI は対象のアプリを起動する(~/Applications/Emacs-plus30.app~ = 30、~/Applications/Emacs-mac29.app~ = 29)。
   Alfred/Spotlight からは「Emacs-plus30」で 30、「Emacs-mac29」で 29 を起動できる。アプリ配置の詳細は
   下の「音声入力 (whisper.el)」→「アプリ配置」を参照。

*** native-comp とビルド差の注意

emacs-plus@30 に移行したことで *両ビルドとも native-comp 有効* になった(旧 emacsformacosx 30 は無効だった)。

- *gcc/libgccjit*: native-comp は ~.eln~ 生成に gcc ランタイムを使う。emacs-plus@30 は ~gcc~/~libgccjit~ を
  Homebrew 依存として自動で入れる。emacs-mac 29 は ~brew install gcc~ が前提(未導入だと
  "ld: library 'emutls_w' not found" で失敗)。
- *初回起動の重さ*: どちらも切替後の初回はパッケージ(約90個)を非同期ネイティブコンパイルするため重く、
  ~eln-cache/30.2-*~ / ~eln-cache/29.4-*~ を生成する。コンパイルは遅延・非同期なので Emacs 自体は使えるが、
  ~*Async-native-compile-log*~ にログが出て CPU を使う。キャッシュが温まれば以降の起動は速い。
- *~straight/build~ は共有*: ~.elc~ は両ビルドで共有される(~.eln~ はビルド別)。通常はそのまま読めるが、
  挙動が怪しいときは ~straight/build~ を作り直す。特に切替直後に transient/magit のエラーが出たら、上の
  「transient / magit の "static-when" エラー」の再コンパイルを実行する。

まとめると、*骨格の手順(link 張り替え + ブランチ切替 + アプリ起動)は両方向で同じ* で、
29 側だけ ~brew install gcc~ が明示的に要る点が違う。

** 音声入力 (whisper.el)

マイク音声を ffmpeg で録音し、[[https://github.com/ggerganov/whisper.cpp][whisper.cpp]] でローカル文字起こしして、ポイント位置に日本語で挿入する。
設定は ~conf/ai-agent.el~。~C-c w~ で録音の開始/停止をトグルする(=whisper-run=)。
モデルは ~large-v3-turbo~、保存先は ~~/.emacs.d/.cache/whisper.cpp/~(git 管理外)。

*** 前提ツール

#+begin_src sh
brew install ffmpeg cmake     # cmake / C++コンパイラ / git は whisper.cpp のビルドに必要
#+end_src

*** macOS ツールチェーンの破損 (Command Line Tools → Xcode に切替)

- *症状*: 初回 ~C-c w~ の whisper.cpp ビルドが ~'array' / 'mutex' / 'cstdio' file not found~ で失敗する。
- *原因*: Command Line Tools(CLT) が壊れており、C++標準ライブラリのヘッダを見つけられない
  (=/usr/bin/c++= が素の ~#include <array>~ すらコンパイル不可)。whisper.el 側の問題ではない。
- *対処*: 正常な Xcode.app に切り替える(要 ~sudo~)。

  #+begin_src sh
  sudo xcodebuild -license accept                              # Apple SDK ライセンス同意
  sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
  #+end_src

  確認: ~echo '#include <array>\nint main(){}' | c++ -x c++ - -o /dev/null~ が通ればOK。
  CLT に依存していた他のネイティブビルド(straight.el 等)も同時に直る。

*** whisper.cpp のビルドとモデル取得

初回の ~C-c w~ で自動的に clone+build+モデルDL(約1.5GB)が走る。手動で先に済ませる場合:

#+begin_src sh
cd ~/.emacs.d/.cache/ && git clone https://github.com/ggerganov/whisper.cpp && cd whisper.cpp \
  && cmake -B build && cmake --build build -j --config Release \
  && bash ./models/download-ggml-model.sh large-v3-turbo
#+end_src

注意: whisper.el は *ビルド失敗時に whisper.cpp ディレクトリを自動削除* する。失敗したら上の
ツールチェーンを直してからやり直すこと。動作確認: ~./build/bin/whisper-cli -m models/ggml-large-v3-turbo.bin -f samples/jfk.wav -nt~。

*** 録音デバイス (avfoundation)

macOS では whisper.el がデバイスを自動選択せず *明示指定が必須*。未設定だと
~Set a suitable value for whisper--ffmpeg-input-device~ で失敗する。

#+begin_src sh
ffmpeg -f avfoundation -list_devices true -i ""   # 音声デバイス番号を確認
#+end_src

~conf/ai-agent.el~ で ~(setq whisper--ffmpeg-input-device ":1")~ のように ~":<音声デバイス番号>"~ を設定。
Bluetooth 機器は接続状況でインデックスがずれることがある。

*** マイク権限 (最重要)

何を話しても「ご視聴ありがとうございました」等の定型文しか出ない場合、*録音が無音* になっている
(=whisper が無音に対して出す幻聴)。app に ~NSMicrophoneUsageDescription~ が無い/マイク権限が無いと、
macOS がマイクを渡さず子プロセスの ffmpeg に無音が流れるのが原因。
=emacs-plus@30= は用途宣言を最初から内蔵しているが =emacs-mac@29= は持たない。いずれも下の
*方法B* で ~com.apple.security.device.audio-input~ entitlement を付けるのが確実(両アプリ適用済み)。対処は2通り。

- *方法A: ターミナルから起動(簡単・元に戻せる)*。macOS はマイクアクセスを「起動元プロセス」に帰属させる。
  端末アプリ(Terminal/iTerm)にマイク権限を与え、=.app= の実行ファイルを *端末から直接* 起動する
  (=open -a= は LaunchServices 経由になり不可)。

  #+begin_src sh
  /Applications/Emacs-mac29.app/Contents/MacOS/Emacs & disown    # emacs-mac 29
  /Applications/Emacs-plus30.app/Contents/MacOS/Emacs & disown   # emacs-plus 30
  #+end_src

  注: =/opt/homebrew/bin/emacs= (Homebrew 版) は *GUI非対応のターミナル Emacs* なので
  ~emacs &~ だと ~suspended (tty output)~ になる。GUI は上の =.app= の実行ファイルを叩くこと。

- *方法B: app を再署名してマイク権限を付与(Dock/Alfred 起動のまま使える)*。
  audio-input entitlement を足して ad-hoc 再署名する。現行 2 ビルドはどちらも hardened runtime 無しの
  ad-hoc 署名なので ~--options runtime~ は不要。*対象ビルドに既存 entitlement があれば必ず含める* こと
  (hardened runtime の app は ~com.apple.security.cs.disable-library-validation~ を持つことがあり、
  落とすと vterm 等のネイティブモジュールが読めなくなる)。

#+begin_src sh
APP=/Applications/Emacs-mac29.app     # 対象アプリ(=/Applications/Emacs-plus30.app= にも同様に)
cp "$APP/Contents/Info.plist" "$APP/Contents/Info.plist.bak"
# 用途宣言が無いビルド(emacs-mac)だけ追加。emacs-plus は内蔵済みなので下行は不要(あってもエラー無視で可)。
/usr/libexec/PlistBuddy -c 'Add :NSMicrophoneUsageDescription string "whisper.el で音声入力に使用します"' "$APP/Contents/Info.plist" 2>/dev/null || true
cat > /tmp/mic.entitlements <<'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0"><dict>
  <key>com.apple.security.device.audio-input</key><true/>
</dict></plist>
EOF
codesign --force --deep --sign - --entitlements /tmp/mic.entitlements "$APP"
#+end_src

  対象アプリを終了してから実行する。Gatekeeper が文句を言うときは
  ~xattr -dr com.apple.quarantine "$APP"~。*アプリを更新・再インストールすると署名は元に戻る* ので都度やり直す。

*** アプリ配置 (Alfred から起動できるように)

emacs-plus / emacs-mac の Emacs.app は Cellar(=/opt/homebrew/...=)にあり Alfred/Spotlight が拾えないため、
ビルドごとに名前を分けて =/Applications= へ *実体コピー(=ditto=)* している(シンボリックリンクは
Alfred のインデックスに乗りにくい)。

- =/Applications/Emacs-plus30.app= = emacs-plus@30(=/opt/homebrew/Cellar/emacs-plus@30/30.2/Emacs.app= のコピー)
- =/Applications/Emacs-mac29.app=  = emacs-mac@29(=/opt/homebrew/opt/emacs-mac@29/Emacs.app= のコピー)

両方に上の *方法B(マイク再署名)* を適用済み。=ditto= で実体コピーしているので、
*対応する formula を ~brew upgrade~ したら* =/Applications= 側へ再コピー＋再署名が必要:

#+begin_src sh
LSREG=/System/Library/Frameworks/CoreServices.framework/Frameworks/LaunchServices.framework/Support/lsregister
# emacs-plus@30 を更新したとき
ditto /opt/homebrew/Cellar/emacs-plus@30/30.2/Emacs.app /Applications/Emacs-plus30.app && "$LSREG" -f /Applications/Emacs-plus30.app
# emacs-mac@29 を更新したとき
ditto /opt/homebrew/opt/emacs-mac@29/Emacs.app          /Applications/Emacs-mac29.app && "$LSREG" -f /Applications/Emacs-mac29.app
# いずれもコピー後に「方法B」の再署名を実行する
#+end_src

注: 両 app とも bundle id は ~org.gnu.Emacs~ で重複するが、Alfred はパス/名前(=Emacs-plus30= / =Emacs-mac29=)で
起動するため実用上は問題ない。

** AIのJSONストリーム受信 (conf/ai-client.el)

AIの応答を「端末の画面」ではなく「構造化イベント」としてEmacsへ取り込む層。
~conf/ai-agent.el~ のCLI統合(claude/agy/bob)はTUIをvtermで動かす方式で、画面には
ANSIエスケープ付きの文字しか来ないため、Emacs側は「いま何が起きたか」を知れない
(セッションを読むには ~my/claude-code-show-session~ で後からJSONLを読み直すしかない)。
ここでは最初から機械可読なストリームを受ける。

*** 構成

扱う提供側は3つ。違うのは「行からJSONを取り出す方法」と「JSONの形」だけなので、
その2つだけを差し替え可能にし(リーダ + 正規化関数)、以降の描画は共通にする。

#+begin_example
プロセス出力 → リーダ(行→JSON) → 正規化関数(JSON→イベント) → 描画 / フック
#+end_example

| 提供側             | リーダ        | ストリーミングの指定方法                                                |
|--------------------+---------------+-------------------------------------------------------------------------|
| claude CLI         | ~stream-json~ | ~--output-format stream-json~(~-p~ と ~--verbose~ が必須)               |
| Gemini API         | ~sse~         | メソッドを変える: ~:generateContent~ → ~:streamGenerateContent?alt=sse~ |
| MyLLM (OpenAI互換) | ~sse~         | エンドポイントは同じまま、bodyに ~"stream": true~                       |

ストリーミングの指定方法は提供側でまったく違う。特にMyLLMは正規のやり方
(メソッドやパスの切り替え)ではなく、bodyのフラグだけでSSEになる独自仕様。

正規化後のイベント種別は ~text~ / ~thinking~ / ~tool-call~ / ~tool-result~ / ~done~ /
~error~ / ~other~ の7つに限る。提供側が増えても描画側は変えない。
知らない種別は捨てずに ~other~ として1行で残す(仕様変更に気付けるようにするため)。

ツール呼び出しの承認や実行は描画とは別の関心事なので、ここでは行わず
~my/ai-stream-event-functions~(フック)を通す。Gemini のように ~functionCall~ を
自分で実行して ~functionResponse~ を返す必要がある提供側では、このフックから実装する。

*** gptel との棲み分け

単発のチャット・リライトは gptel(~conf/ai-agent.el~ 第6節)の方が良く出来ているので
そのまま使い、ai-client は「エージェントの動きをEmacs側で受けて描く」用途だけを持つ。

*** 前提

- claude … ~claude~ CLI がPATHにあること。APIキーではなくCLI側のログインで動く。
  ~stream-json~ は ~--print~(-p)と ~--verbose~ の併用が必須
  (無いと =When using --print, --output-format=stream-json requires --verbose= で起動に失敗する)。
- Gemini … ~curl~ と環境変数 ~GEMINI_API_KEY~。APIキーはコマンドライン引数に置かず、
  URL・ヘッダ・本文をまとめたcurl設定を標準入力から渡す(~ps~ の出力に鍵を出さないため)。
- MyLLM … ~curl~ と ~MY_LLM_HOST~ / ~MY_LLM_ENDPOINT~ / ~MY_LLM_API_KEY~。
  サーバ側がSSEに対応しているモデルが ~gemini-*-flash~ / ~claude-haiku-*~ /
  ~claude-sonnet-*~ / ~claude-opus-*~ に限られるため、
  ~my/ai-stream-myllm-sse-models~ で絞り、非対応のモデルは起動前に弾く
  (非対応モデルに ~stream: true~ を投げるとSSEではない応答が返り、
  ~data:~ 行が1つも来ないまま何も表示されずに終わるため)。
  モデルは ~my/ai-stream-myllm-model~、未設定なら ~MY_LLM_FAST_MODEL~、
  それも無ければ実行時に選ぶ(一覧はgptelのMyLLMバックエンドから借りる)。
  指定は完全一致ではなく部分一致で扱う。サーバ側のモデルは日々版が上がるため
  (~gemini-3.6-flash~ → ~gemini-3.7-flash~ 等。接続先はおそらくBedrock経由で、
  ゲートウェイがモデルIDを付け替えている)、完全一致で持つと版が上がった日から
  存在しないモデルを指してしまう。~"gemini"~ のように版を含めず書いておけば追随する。
  一覧に一致するものが無ければ知らせて選び直させる(黙って別のモデルに落とさない)。
  一覧自体が古いときは ~M-x my/gptel-myllm-refresh-models~ で取り直す。

OpenAI互換だけはツール呼び出しの届き方が違う。claude/Geminiは1イベントに引数まで
揃って来るが、OpenAI互換は ~delta.tool_calls~ の ~function.arguments~ が
JSON文字列の断片として複数チャンクに割れて届くため、~index~ ごとに溜めて
~finish_reason~(または ~[DONE]~)の時点で1件にまとめている。

*** キーバインド

~conf/keybind-manage.el~ の「AIのJSONストリーム受信」節(~SPC a j~ 配下)。
バッファ内では ~TAB~ で思考(thinking)の開閉、~C-c C-k~ で中止。

** メール (mu4e)

マウスを使わずEmacs内でメールを読み書きするための設定。設定は ~conf/mail.el~、キーバインドは
~conf/keybind-manage.el~ の「メール (mu4e)」節(~SPC M~ 配下)。

役割分担は下記のとおりで、Emacs自身はIMAP/SMTPを喋らない(通信を外部コマンドに任せることで、
同期中にEmacsがブロックされず、CLIからも同じ状態を再現できる)。

| 役割           | コマンド | 備考                                                     |
|----------------+----------+----------------------------------------------------------|
| 受信(IMAP同期) | mbsync   | isyncパッケージ。IMAP ⇔ ローカルMaildir(~~/Mail~)        |
| 索引・検索     | mu       | Maildirをインデックス。mu4eのelispもこれに同梱される     |
| 送信(SMTP)     | msmtp    | パスワードはmacOSキーチェーンから取り出す                |

*** straight管理外である理由

mu4e の elisp は MELPA ではなく検索エンジン本体 ~mu~ に同梱されて配布され、elispとバイナリの
バージョンが食い違うと動かない。そのため mu4e だけは lockfile での固定から外し、Homebrewの
~mu~ を正として ~:straight nil~ + load-path 追加で読み込んでいる。~conf/mail.el~ は ~mu~ の実行
ファイルから同梱elispの場所を逆算し、*見つからなければ設定ごとスキップ* するので、mu を入れて
いないマシンでも起動時にエラーにはならない(~SPC M m~ が未定義になるだけ)。

*** 導入手順

#+begin_src sh
brew install mu isync msmtp
#+end_src

**** 1. アプリパスワードをキーチェーンへ

IMAP/SMTPに繋がらない)。mbsyncとmsmtpの両方から同じ項目を参照する。

#+begin_src sh

# プロンプトにアプリパスワード(16桁、空白なし)を貼る

**** 5. 環境変数

このリポジトリは公開しているため、アドレス等の個人情報はファイルに書かず環境変数で渡す
(gptelのAPIキーと同じ方針)。~.zshrc~ に下記を追加する。

#+begin_src sh
export MY_MAIL_ADDRESS="you@gmail.com"
export MY_MAIL_FULL_NAME="Your Name"
#+end_src

*** キーバインド

| キー      | 動作                                    |
|-----------+-----------------------------------------|
| ~SPC M m~ | mu4e を開く                             |
| ~SPC M c~ | 新規メール作成                          |
| ~SPC M s~ | 検索(mu のクエリ構文)                  |
| ~SPC M u~ | 今すぐ受信(mbsync)して索引を更新        |

mu4eのバッファ内(一覧・本文・作成)のキー操作は evil-collection の mu4e サポートに任せている
(~conf/mail.el~ で ~(evil-collection-init 'mu4e)~ を呼ぶ)。移動が ~j/k~ になるなどvim風に
置き換わるため、mu4e標準のキーとは一部異なる。実際の割り当ては各バッファで ~?~ または
~C-h m~ で確認する。

*** 運用メモ

- 受信は5分ごとの自動更新(~mu4e-update-interval~)。手動で取りに行くときは ~SPC M u~。
- mbsyncはファイル名を書き換えるため ~mu4e-change-filenames-when-moving~ を ~t~ にしている
  (~nil~ のままだと同期のたびにメールが重複する)。
- 送信控えはGmailがサーバ側で作るので、ローカルには保存しない設定にしている。
- 本文の文字コードはUTF-8を優先させている。init.elで日本語環境にしている都合で、既定のままだと
  ISO-2022-JPで送信され、絵文字や機種依存文字が化けるため。

** 別マシンへの移行 (straight.el)

パッケージは straight.el で管理しており、~straight/versions/default.el~ にバージョンを固定した lockfile をコミットしている。

- 新しいMacでの初回起動時、init.el が straight.el 自身をbootstrapし、各パッケージを lockfile に記録されたコミットで取得する
- lockfile を更新したいとき（新しいパッケージを追加した/意図的に最新化したいとき）は、Emacs上で ~M-x straight-freeze-versions~ を実行してから差分をコミットする
- straight関連のエラーで詰まったときは、まず ~M-x straight-thaw-versions~ でlockfile通りの状態に戻せるか試す
- 「ローカルのgit remoteとレシピのURLが食い違う」旨のエラーが出た場合、該当パッケージが上流でリポジトリ移動した可能性が高い。~straight/repos/<package>~ と ~straight/build/<package>~ を削除して再起動すれば再取得される
- lockfileで復元できるのはEmacsパッケージだけで、*外部コマンドは別途インストールが必要*。上記「前提 > 必要なもの」の表を参照(go-grip、Node.js、Go など)
